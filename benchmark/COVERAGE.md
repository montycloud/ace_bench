# Scenario ↔ CFN Coverage Map

**What can we actually check with the CloudFormation fixtures we have today?**

This is the tracking sheet for fixture coverage: which CFN template backs which scenario, and
which scenarios we **cannot** fully evaluate from a fresh deploy (and why). It is generated by
cross-referencing every gold-label resource handle in
[`gold_labels/agnostic_overlay.py`](gold_labels/agnostic_overlay.py) against the CloudFormation
**Outputs** actually defined in [`fixtures/`](fixtures/).

> **How "checkable" is decided.** Each scenario's `correct_resources` / `should_not_flag` are
> `{{stack:OutputKey}}` handles. A scenario is **checkable** only if *every* handle maps to a
> template that (a) exists in `fixtures/` **and** (b) actually declares that `OutputKey`. This
> is a **static** check of template Outputs — it confirms the wiring is complete, but the
> handles still need a one-time **live-manifest validation** on first real deploy
> (`python -m runner.provisioner`), exactly as the overlay's header warns.

## Templates that back no scenario (deployed anyway, or dangling)

### Deployed as realism / "must-not-flag" decoys (present, correct)

These templates are deployed to make the environment realistic — healthy compliant resources
the agent must **not** flag, plus supporting infra — even though no gold label names their
specific Outputs. They contribute to the **Safety** pillar broadly (over-flagging is penalized):

`AnomalyDetectionCompliant.yml` · `ApiGatewayCompliant.yml` · `BudgetsCompliant.yml` ·
`BudgetsNonCompliant.yml` · `CloudWatchCompliant.yml` · `CostOptimizerHubCompliant.yml` ·
`LambdaCompliant.yml` · `S3Compliant.yml` · `SNS-Complaint.yml` · `SQSCompliant.yml` ·
`SecurityGroupCompliant.yml` · `SubnetCompliant.yml` · `VPCSGCompliant.yml`

> `BudgetsNonCompliant.yml` deploys but exposes **no resource Outputs** — the budgets scenario
> is account-level (see the account-level group above), so this is expected, not a bug.

### ⚠️ Dangling reference — templates that do NOT exist

`deploy.sh` invokes **`IAMCompliant.yml`** and **`IAMNonCompliant.yml`** by name (compliant,
non-compliant, and combined paths), but **neither file exists** in `fixtures/`. Because the
call is written `launch_stack … && launched+=(…)`, the failure is swallowed and the IAM stack
is silently skipped — the rest of the deploy is unaffected.

**Impact on coverage: none.** No scenario's gold labels reference a `wafr-*-iam` stack. The
IAM/least-privilege scenarios (`over-privileged-roles`, `refactor-wildcard-policies`,
`preventive-control-guardrail`) get their wildcard role from
**`LambdaNonCompliant.yml → FailingLambdaExecRole`**, which exists. So the two missing IAM
templates are a **dangling `deploy.sh` reference to clean up**, not a coverage gap. Fix by
either removing the two `launch_stack …-iam` lines or authoring the templates.

## Caveats & how to re-verify

1. **Static, not live.** This map confirms each referenced `OutputKey` is *declared* in a
   template. It does **not** prove the stack deploys cleanly or that physical IDs resolve. Run
   `python -m runner.provisioner --region <r>` after a real deploy; any scenario reporting
   `_unresolved` handles means an OutputKey drifted — fix it in `agnostic_overlay.py`.
2. **LocalStack is narrower.** The offline path covers even fewer services (Community edition
   can't do S3-Express, WAF, Budgets, Compute Optimizer, or Lambda-backed custom resources).
   This map is for the **real-AWS** deploy, which is the superset.
3. **Regenerating this doc.** The tables are derived, not hand-maintained — re-run the parse in
   the release-prep notes (cross-references `agnostic_overlay.py` against `fixtures/*/*.yml`
   Outputs) whenever scenarios or fixtures change.
